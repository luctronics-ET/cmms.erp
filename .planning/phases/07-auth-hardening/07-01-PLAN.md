<objective>
Replace djb2 password verification with Argon2id, using a dual-hash lazy-upgrade
strategy so NO existing account (human or external-module service account) is locked
out. On the first successful login with a legacy djb2 hash, re-hash the password to
Argon2id and persist it in the same request. This plan implements SEC-01 only and
proves — via tests — that no existing account is locked out, which is the
precondition the next plan (default-password removal) depends on.

Purpose: djb2 is a non-cryptographic hash and unacceptable for passwords. Argon2id is
the PHC winner (per STACK.md). Lazy upgrade migrates accounts transparently with zero
forced password resets and zero changes to external modules (xPredial, aguada-web, PMOC)
that call POST /api/auth/login.

Output: argon2-cffi dependency, rewritten login verification path, new tests/test_auth.py.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| external module -> POST /api/auth/login | xPredial / aguada-web / PMOC service accounts submit {mat, senha} over the internal network; the credential and the stored hash cross here |
| browser ERP -> POST /api/auth/login | Human users submit plaintext password; verification + hash upgrade happen server-side |
| login handler -> usuarios table | Plaintext password is hashed and the new Argon2 hash is written back (lazy upgrade) |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-07-01 | Information Disclosure | pw_hash storage (djb2) | high | mitigate | Replace djb2 verification with Argon2id; lazy-upgrade every account's stored hash on first login so cracked-in-seconds djb2 hashes stop being authoritative |
| T-07-02 | Spoofing | POST /api/auth/login legacy path | high | mitigate | Keep _djb2 as a verify-only comparator; never emit new djb2 hashes; argon2 errors map to 401 (no info leak on which check failed) |
| T-07-03 | Denial of Service | lazy upgrade UPDATE on login | low | accept | One extra indexed UPDATE per account, once (first login only); negligible on an internal-network CMMS |
| T-07-04 | Tampering | Account lockout via verification refactor | high | mitigate | Mandatory test (tests/test_auth.py) proves a djb2 account and a service account both log in successfully BEFORE the default-removal plan runs |
| T-07-SC | Tampering | pip install argon2-cffi | high | mitigate | argon2-cffi is the PHC reference binding, verified in STACK.md against PyPI (25.1.0, June 2025); pinned exact version. See legitimacy note below. |
</threat_model>
